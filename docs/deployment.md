# 部署与更新

## 文件与相对路径

`local/` 放原始订阅、基础网络配置和验收映射；`output/` 是含节点凭据的运行产物；`reports/` 是测速数据。三个目录全部被 Git 忽略。不要使用 `git add -f` 提交这些目录。

生成的 `providers/*.yaml` 是各业务自己的节点副本。即使节点参数相同，各服务也拥有独立的检查对象。仅复制 `config.yaml` 会丢失这些文件来源。

独立 Mihomo 使用 `-d output -f output/config.yaml`。执行 `-t` 只检查配置，不切换当前系统代理。实际启动前关闭占用相同代理端口的其他核心，或在本机基础配置设置不同 `mixed-port`。

## Clash Verge Rev

1. 备份当前生效配置、增强脚本和组选择；这些备份留在本机。
2. 根据客户端实际内核工作目录，将生成的 `providers/` 放在对应目录下；相对路径从内核工作目录解析。绝对路径也必须位于内核 HomeDir 或其明确允许的 SAFE_PATHS 中，不能任意引用外部目录；优先使用工作目录内的相对路径。这些本机路径不能提交。
3. 将生成配置作为本地配置导入并切换。不要直接覆盖客户端生成的 `clash-verge.yaml`；客户端下次生成会覆盖手动修改。
4. 查运行态节点来源、组与规则，验证实际请求经过指定组。仅在磁盘看到新 YAML 不足以证明加载成功。
   特别核对每个 provider 的实际导入数量；来源刷新出现缺文件 / 503 或数量为 0 时，先检查服务内核的工作目录与实际文件，再验证备用路径。
5. 复测 GitHub 网页、Raw、API、源码下载与 `git ls-remote`；AI 页、匿名接口和已登录生成分别验收。

不同客户端版本的内核工作目录可能不同，公开生成器没有绑定私人 profile ID、Windows 用户目录或命名管道。已有持久增强脚本环境可以把本项目的分类和独立来源结构移入持久脚本，并再次对比生成配置与运行态。

## 更新订阅

本工具读取本机导出文件，不保存或请求订阅 URL。TAG / Flower 等订阅限制按供应商及客户端条件处理。订阅更新后需要重新导出、重建并重载；生成文件不会自行实时同步。

节点改名、消失或重复名称会让映射检查失败，应在本机更新设置。新增节点自动出现在手动目录，只有填写倍率并取得对应服务验收后才能进入自动池。节点参数中的 `dialer-proxy` 等依赖原策略组的字段需要按新结构调整，再通过内核检查；本工具不自动猜测这些引用。

`base` 保留 DNS/TUN/hosts 等网络字段，但清除原始 `proxies`、`proxy-groups`、`proxy-providers`、`rule-providers`、`rules`。如原配置依赖外部规则来源，需要经过审查后加入新模板；不要假定原订阅的全量国内和广告规则仍然存在。

没有提供 `base` 时是系统代理使用的基础配置，没有自动开启 TUN，也没有完整的国内 IP 分流。TUN 和代理 DNS 要用实际解析路径与泄露测试验收，不应因“系统代理开启”就宣布整机 DNS 已被代理。

## 恢复

恢复先前备份的本地配置和组选择并重载，再核对运行态。生成器默认写 `output/`，也接受被忽略的 `local/` 子目录；生成过程不会改变客户端或关闭旧连接。预算保护切换的额外步骤见 [额度保护](quota-and-failover.md)。

## 可选后台监测

`tools/watch.py` 接管已经用本项目生成并加载的独立 Mihomo 完整配置，设置与台账放在 `local/`，候选产物放在设置旁的 `policy-output/`。它先在内核工作目录暂存并校验，再替换正式配置与 providers，保存首次备份；控制器重载失败时恢复本次修改前的文件并重载。普通候选调整在有现有连接时延后，额度锁定立即执行。完整接入步骤见[后台保护指南](policy-monitoring.md)。

Clash Verge Rev 的 merge 片段与增强 JavaScript 不是完整配置，不能交给这个独立部署器覆盖。`tools/verge_policy.js` 提供转换函数，需要在现有持久增强脚本中接入；客户端的生成、重载、工作目录与账单监测仍需适配并验收。不要同时运行两个管理同一配置的后台程序。
